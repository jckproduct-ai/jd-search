## M0 — DART 스파이크

**설계서에 적어 둔 "정형 API로 70% 확보"는 근거가 없었습니다.** 재 보니 35곳 중 2곳(5.7%)이었습니다.

길은 정형 API가 아니라 **감사보고서 원문 표 파싱**이었고, 그쪽이 20곳 중 16곳(80%)이었습니다.
최종 확보율 98곳 중 61곳(62.2%).

스파이크에서 나온 가장 값진 사실은 커버리지가 아니라 이것이었습니다 — **DART는 키가 필요 없습니다.**
웹 공시검색 화면에 corp_code·법인등록번호·재무제표가 전부 있습니다.
사용자에게 요구하는 필수 키가 **2개에서 1개로** 줄었고, 이 숫자는 이후 모든 기능 판단의 기준선이 됩니다.

파서 함정 3건을 기록해 뒀습니다. 셋 다 조용히 틀리는 종류입니다.

- 뷰어 목차가 `viewDoc(a,b,…)` 6인자인 줄 알았는데 `cnt['dcmNo'] = "…"` 순차 할당이었습니다 → 20곳 전부 "파싱 실패"
- 주석 컬럼(`23,28`)을 금액으로 집으면 **매출 41.9조가 23.3억이 됩니다**
- **적자면 계정명이 "영업손실"이 되고 값은 양수로 적힙니다.** 부호가 숫자가 아니라 라벨에 실려 있습니다

## M3 — 살아있는 공고만 보여준다는 약속 지키기

README가 이미 "살아있는 공고만"이라고 적어 놓고 있었는데 실제로는 확인하지 않고 있었습니다.

- **3상태 판정** alive / closed / **unknown** — 🔴 네트워크 오류를 마감으로 굳히지 않습니다
- **마감 근거는 상태 표시뿐** — 마감일 경과는 쓰지 않습니다(상시 전환·연장이 흔합니다)
- **재검색 대조는 회사 ID 완전일치** — 회사명 `includes`는 "미소 → 미소무역" 함정을 그대로 재현합니다
- **같은 자리 연결은 제목 유사도 ≥0.8이 정확히 1건일 때만**

🔴 구현 직후 실측에서 **되찾기가 잡음 주입으로 번지는 것**을 잡았습니다.
기획 자리를 되찾으려다 같은 회사의 `Senior Backend Engineer`가 목록에 들어왔습니다.
**조용한 손실을 막으려다 조용한 잡음을 만든 것**이라, 되찾는 대상을 ① 같은 자리로 연결된 것
② 내 직군에 걸리는 것으로 좁히고 나머지는 건수·제목만 알립니다.

이 시점에 **단계 간 계약 통합 테스트**를 신설했습니다(임시 `JD_SEARCH_HOME`에서 실제 프로세스로 실행).
**신설하자마자 실제 결함을 잡았습니다** — 이미 존재하는 디렉터리의 권한이 안 고쳐지고 있었습니다.

착수 전에 재 봤고, 설계서에 없던 사실이 나왔습니다.

**이 보드는 "전수조사"가 성립하지 않습니다.** 그래서 페이지 상한이 아니라
**제목 매치율이 바닥나는 지점**에서 멈추고, **어디서 왜 멈췄는지를 리포트에 적습니다.**
모르는 것을 모른다고 적는 쪽이, 다 봤다고 말하는 쪽보다 낫습니다.

### 보드마다 판정 신호를 분리했습니다

새 보드 모듈은 기존 보드와 **같은 모양의 레코드**를 돌려주되 **마감 판정 신호는 완전히 분리**했습니다.
하나의 규칙으로 묶으면 둘 중 한쪽은 반드시 틀립니다.

| 심각도 | 내용 | 조치 |
|---|---|---|
| P1 | 🔴 **본문이 이미지뿐인 공고가 흔합니다**(14건 중 3건). 글자 없는 JD 파일이 "내용 있는 기록"으로 세어져 다시 받지 않음 → 공고가 내려가면 영구 손실 | `imageOnly`/`failed`/`empty` 구분 + 이미지 주소 저장 |
| P1 | 목록 마감 표기에 **연도가 없습니다**(`~ 09/20`) — 추정하면 12월→1월에서 통째로 틀립니다 | 상세 값만 사용 |
| P1 | 🔴 **근무지가 여러 곳**인데 목록은 첫 곳만 줍니다 | 전부 보관 + **하나라도 들면 통과** |
| P1 | 다중 근무지에서 **시·도 생략 항목**("서초구")이 전국의 같은 이름 구를 물어옴 | 앞 항목의 시·도를 물려받음 |
| P1 | **상시채용·채용시 마감이 22%**(40건 중 9건) — 날짜 경과로 판정하면 이만큼이 통째로 죽습니다 | 상태 블록 4형태로만 판정 |
| P1 | 보드가 둘인데 실행 기록을 공유해 **한 보드가 다른 보드의 부분 실패 경고를 덮어씀** | 보드별로 분리 |

### 🔴 병합 — 실측이 임계값이 아니라 비교 대상을 바꾼 지점

실제 교차 보드 중복 1건이 나왔는데 유사도 **0.64로 보류**됐습니다.

```
보드 A  "서비스기획 팀원 (부산)"
보드 B  "서비스기획 팀원 (신입~5년 이하 / 부산)"
```

안전 쪽으로 동작한 건 맞지만 이러면 **병합이 사실상 0건**입니다.
**임계값을 낮추는 대신 비교 대상을 고쳤습니다** — 괄호 안이 경력·지역·고용형태뿐일 때만 떼고 비교합니다.
경력과 지역은 이미 따로 대조하고 있어서 **두 번 세고 있었던 것**입니다.
`"프로덕트 매니저 (커머스)"` vs `"(물류)"`는 여전히 다른 자리로 남습니다(테스트로 못 박았습니다).
→ 재실행에서 **유사도 1.0으로 병합 성공.**

병합 원칙은 **틀리는 방향의 비대칭**에서 나옵니다.
안 합치면 중복이 눈에 보이지만, **잘못 합치면 서로 다른 자리 하나가 목록에서 조용히 사라집니다.**
그래서 불확실하면 합치지 않고 "중복일 수 있음"으로 표시만 합니다.

### 편집 화면을 두 벌로 만들지 않았습니다

리포트 템플릿에 확장 지점을 두고 로컬 서버가 편집 계층만 얹습니다.
UI가 두 벌이면 한쪽만 고쳐지고 둘이 갈라집니다.

보안 네 겹 — **127.0.0.1 바인딩 · 매 실행 랜덤 토큰 · Host 검사(DNS 리바인딩) · 쓰기 Origin 검사(CSRF)**.
브라우저를 자동으로 열지 않습니다. 실측으로 5가지 우회를 전부 403 확인했습니다.

🔴 **"삭제"는 숨김입니다.** 레코드와 JD 원문은 남습니다 — 같은 자리가 새 ID로 재공고되므로
지우면 이력이 끊겨 **같은 회사에 두 번 지원하게 됩니다.** 화면 문구에도 "삭제가 아닙니다"라고 적었습니다.

### 동명이인 — 답을 알아도 반영할 수 없던 문제

전에는 콘솔에 후보만 찍고 미확인으로 뒀습니다. **같은 질문이 매 실행 반복됐습니다.**

- 🔴 **결정과 함께 재무 캐시를 지웁니다.** 판정 로직만 고치고 캐시를 두면 다음 실행이 옛 결과를 그대로 씁니다
- 🔴 **"모르겠음"도 결정으로 저장합니다.** 안 그러면 질문이 영원히 반복됩니다

## 테스트 — 129 → 161 → 293 → 308 → 317 → 320 → 338 → 415 → 442

숫자보다 중요한 건 **테스트가 실제로 무는지 확인했다는 것**입니다.
고친 로직을 일부러 되돌려 보고(뮤테이션), 테스트가 잡는지 봤습니다.

🔴 **그 과정에서 테스트 자체의 결함을 하나 잡았습니다.**
병합 가드 테스트가 `why`(사유)만 보고 `same`(판정)을 안 봐서, **지역 검사를 통째로 뒤집어도 통과**했습니다.
판정을 함께 검사하도록 고쳤습니다.

부수적으로 알게 된 것 — `fetch`는 `Host`를 금지 헤더로 막습니다.
DNS 리바인딩 방어를 테스트하려면 raw `http.request`를 써야 합니다.

## 공개 직후 외부 검증 (2026-08-10)

공개하고 나서 **처음 보는 사람 관점**으로 외부 모델에 저장소 전체를 검증시켰습니다.
"문서가 코드에 대해 거짓말하는 곳을 찾아라"가 첫 번째 지시였습니다.

🔴 **7건이 나왔고, 그중 4건이 이 저장소가 스스로 세운 기준을 어기고 있었습니다.**

| 발견 | 왜 아팠나 |
|---|---|
| `profile.example.yml`이 통근 상한을 `초과분은 목록에 아예 올라오지 않는다`고 약속 | **통근 실측은 미구현입니다.** 신규 사용자가 가장 먼저 복사하는 파일이라 노출 확률이 가장 높았습니다. 게다가 이건 이미 "✅ 완료"로 마감한 개선 항목(#21)의 **회귀**였습니다 |
| 스킬 설명문이 `통근 시간 확인에 사용한다`고 광고 | 에이전트가 스킬을 고르는 근거 문장입니다. "통근 얼마나 걸려?"에 이 스킬이 발동해서 못 한다고 답하는 구조였습니다 |
| 등급표에 `자본총계 < 0`, 코드는 `<= 0` | 이 `≤`가 바로 값을 치르고 고친 경계값(#8)입니다. 고쳐 놓고 문서에 반영을 안 했습니다 |
| 테스트 건수가 문서마다 달랐음 (293 vs 308) | "근거 없는 숫자를 말하지 않는다"를 내세운 저장소에서 자기 숫자가 갈렸습니다 |
| 사람인 HTML 파싱을 `api`로 분류 | `api`는 "공식 API"라고 스스로 정의해 놓고 공개 페이지 파싱을 같은 이름에 넣었습니다. **동의 절차가 필요한 방식과 아닌 방식의 경계가 흐려집니다** → `web` 모드를 따로 만들었습니다 |

마지막 건을 고치다 **더 나쁜 걸 하나 더 찾았습니다.** 수집 스크립트가 `sources` 값을 `=== 'off'`로만 봤습니다.
`offf` 같은 오타를 적으면 **사용자는 껐다고 믿는데 계속 긁습니다.** 아는 값만 통과시키도록 바꾸고 테스트 9건을 붙였습니다.

> 이 일곱 건에 공통점이 있습니다. **전부 문서였고, 전부 자기가 세운 규칙을 자기가 어긴 것**이었습니다.
> 코드는 규칙을 지키고 있었는데 문서가 못 따라갔습니다. 규칙을 크게 적어 두는 것만으로는 안 지켜집니다 —
> 지킨 걸 **검사하는 장치**가 있어야 합니다. 그래서 나온 것들은 가능한 한 테스트로 옮겼습니다.

## 확보율 재측정 — 표본을 14건에서 150건으로 (2026-08-10)

README에 사람인 확보율을 싣지 않고 있었습니다. **표본이 14건짜리였기 때문입니다.**
전국·키워드 11개로 다시 쟀습니다 — 공고 150건, 회사 135곳.

| | |
|---|---|
| 확보 | **66/135 (48.9%)** |
| 출처 | 공공데이터포털 36 · DART 감사보고서 27 · 둘 다 3 |
| 미확인 69곳 | DART 미등록 60 · 2023년 이후 공시 없음 6 · 동명이인 1 · 자료 노후 1 · 항목 부족 1 |

🔴 **보드가 다르면 확보율도 다른데, 원인이 파서가 아니었습니다.**
원티드 표본에서는 미확인 15곳 중 4곳(27%)이 "붙이면 안 돼서"(동명이인) 미확인이었습니다.
사람인 표본에서는 그게 1곳뿐이고, 대신 **DART 미등록이 69곳 중 60곳(87%)** 입니다.
같은 코드가 같은 순서로 도는데 결과가 갈립니다 — **그 보드에 올라오는 회사가 다르기 때문**입니다.
사람인에는 외부감사 대상이 아닌 규모의 회사가 그만큼 많습니다. 확보율을 한 숫자로 말하면 안 되는 이유가 여기 있습니다.

### 재는 김에 두 가지가 더 나왔습니다

**① 세어 보지도 않은 것을 단정하고 있었습니다.**
사람인 수집이 끝날 때마다 `원티드와 겹치는 공고가 있습니다`를 찍었습니다. 원티드를 끄고 사람인만 받은
이번 실행에서도 그대로 떴습니다 — 겹칠 대상이 0건인데 병합을 돌리라고 합니다.
"잘린 사실을 적는다"를 내세우는 도구가 **확인하지 않은 사실을 단정하면 나머지 경고도 같이 신뢰를 잃습니다.**
다른 보드 공고 수를 실제로 세고, 0이면 아무 말도 하지 않도록 고쳤습니다.

**② 사람인은 국문·영문 상호를 슬래시로 병기합니다** — `(주)아이클레이브 / iclave`.
괄호 병기(`미소(Miso)`)는 쪼개서 후보를 만들면서 슬래시는 안 쪼갰습니다.
**그 이름의 법인은 어디에도 없으니** 모든 후보가 빗나가고 조용히 미확인이 됩니다.
다만 정직하게 적자면 — **이번 표본에서 실제 손실은 0이었습니다.** 해당 2곳을 국문 상호로 직접 조회해 보니
애초에 DART 미등록이었습니다. 고친 이유는 손해를 봐서가 아니라 **손해가 났어도 알 수 없는 구조**였기 때문입니다.
(이름 속 슬래시 `에이/비스토어`까지 쪼개면 없는 회사를 만들어 냅니다 — 공백으로 둘러싸인 것만 봅니다.)

### 그리고 이 숫자가 기본값을 바꿨습니다

목록에서 **유니크 1035건**이 나왔는데 상세 조회 기본 상한은 200이었습니다. **첫 목록이 19%였다는 뜻입니다.**
잘린 사실은 리포트 맨 위에 적히고 있었습니다. 그래도 바꿨습니다 —
**처음 만들어진 목록이 5분의 1이면 사용자는 그 5분의 1을 자기 시장 전부로 읽습니다.**
경고 한 줄로는 첫 화면이 만드는 오해를 못 막습니다. 가장 비싼 오해가 가장 먼저 생깁니다.

→ **첫 실행은 상한 없이 전량.** 다만 말 없이 30분을 쓰지는 않습니다 —
시작 전에 몇 건을 받고 몇 분 걸리는지, 줄이려면 어떻게 하는지를 먼저 적습니다.
두 번째 실행부터는 다시 200입니다.

🔴 **고치면서 더 나쁜 걸 하나 찾았습니다.** 상한이 **후보 건수**를 세고 있었습니다.
재실행 때 앞 200건이 전부 이미 받아 둔 것이어도 예산이 소진돼,
**목록 뒤쪽의 새 공고는 영영 안 받아집니다.** 네트워크를 쓰지도 않는 건이 예산을 먹고 있었던 것입니다.
상한이 세는 것을 **실제로 받아야 하는 건수**로 바꿨습니다.

이 규칙은 스크립트 본문이 아니라 `planDetailBudget`이라는 순수 함수에 뒀습니다.
바로 위에서 "스크립트 본문의 출력 문구는 테스트가 못 문다"고 적어 놓고 같은 자리에 규칙을 또 둘 수는 없었습니다.

### 정렬 기본값 — 위험 먼저에서 좋음 먼저로

`등급순` 정렬이 **위험을 맨 위**에 올리고 있었습니다. 경고를 먼저 보여 주는 건 이 제품의 성격과 맞지만,
**이 화면에서 사용자가 하려는 일은 지원할 곳을 고르는 것**입니다. 위험이 위에 깔리면 정작 볼 것이 바닥에 갑니다.

→ 기본을 `좋음 먼저`로 바꾸고 `위험 먼저`를 따로 남겼습니다. 라벨이 방향을 말합니다.
미확인은 양쪽 다 맨 뒤입니다 — 좋은 것도 나쁜 것도 아니라 **아직 모르는 것**이라서입니다.
